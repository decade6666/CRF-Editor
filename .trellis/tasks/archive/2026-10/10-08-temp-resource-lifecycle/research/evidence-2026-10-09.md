## Design-relevant constraints confirmed

- Magic-before-size order is load-bearing: today a 300MB non-SQLite file gets the SQLite message (magic :81 precedes size :83). Streaming must preserve this (R1 explicitly requires it).
- `_save_bytes_to_temp` writes to the system temp dir, not `uploads/docx_temp`; the request deletes it in `finally`. Crash leftovers in the system temp dir are never swept by anything in-process → R4's motivation for moving `.db` uploads into the owned, swept directory.
- `save_temp_file`'s bytes API must survive (perf script :179 + `test_docx_temp_isolation.py` depend on it); the streaming path shares naming/limit constants with it instead of duplicating them.

## Framework boundary facts (verified 2026-10-09, second revision round)

- Pinned stack: FastAPI 0.110.3, Starlette 0.37.2, Python 3.10.21 (venv `/home/decade/.venvs/crf-editor`).
- `UploadFile` endpoints: Starlette resolves `request.form()` **before** the endpoint runs (`starlette/requests.py:280` → `MultiPartParser.parse()`); each file part spools into `SpooledTemporaryFile(max_size=1024*1024)` (`starlette/formparsers.py:121` class default, `:209` per part) — ≤1 MiB RAM, then disk rollover in the default temp dir. Endpoint-level chunked `read(n)` therefore removes only the endpoint's whole-file RAM detour (the streaming path still copies spool → managed temp file, so both paths write the managed disk file); network transfer and multipart spool precede the endpoint and are out of the task's promise.
- Magic literal `b"SQLite format 3"` is **15 bytes**; the current `content[:16].startswith` check passes any content whose first ≥15 bytes match (no trailing-NUL requirement) and rejects EOF-short files. Streaming must reproduce exactly this (`startswith`, accumulate to ≥15 bytes or EOF).
- `asyncio.CancelledError` inherits from `BaseException` on Python ≥3.8 — `except Exception` cleanup leaks partial files on client disconnect.

## Threadpool semantics + shared-writer facts (verified 2026-10-09, third revision round)

- Pinned anyio 4.15.1. `run_in_threadpool` (`starlette/concurrency.py:36-42`) delegates to `anyio.to_thread.run_sync` without overriding options; the default is `abandon_on_cancel=False` (`anyio/to_thread.py:30`) — on task cancellation the event loop waits for the worker thread to finish before delivering the cancellation. `asyncio.to_thread` abandons immediately.
- Import services only `flush` (`project_import_service.py` `with perf_span("flush"): session.flush()` at :263 and :315); the commit/rollback lives in `get_session`'s `with session.begin(): yield session` teardown (`database.py:1398-1404`). Consequence: the three session-bearing import calls must use `run_in_threadpool` — cancellation is delivered only after the worker completes, so the teardown observes a finished call and rolls back; `asyncio.to_thread` would let the teardown run concurrently with the abandoned worker on the same Session.
- Starlette `UploadFile` for a non-in-memory spool already delegates `read`/`write`/`seek`/`close` to `run_in_threadpool` (`starlette/datastructures.py:451-475`, write at :458, read at :463). A per-chunk `run_in_threadpool(handle.write, chunk)` in a helper therefore mirrors the framework's own write path, and the non-abandon guarantee ensures an in-flight chunk finishes before cancellation reaches the cleanup.
- `DocxScreenshotService.cleanup_old_caches` deletes **directories only**: `docx_screenshot_service.py:750-768` iterates the base dir, `if not temp_dir.is_dir(): continue`, then `shutil.rmtree` — loose `.db` files migrating into the same parent dir are never touched by it.

## `.db` stored-name final form (2026-10-09, final revision round)

- Today's `_save_bytes_to_temp` stores via `tempfile.mkstemp(suffix=...)` — the uploaded filename never enters the path (only its suffix does). Any owned-naming scheme that embeds the uploaded stem would regress: a ~250-char name + the 40+ char prefix exceeds NAME_MAX (255 bytes) → `os.open` raises `OSError(ENAMETOOLONG)` → today-succeeding import becomes an unhandled 500; embedded NUL/odd characters would surface as confusing errors. The `.db` file is consumed in-request; nothing downstream reads its name.
- Final decision: `build_owned_db_filename(*, user_id)` (no filename param) mints `{temp_id}_u{uid}_p0_upload.db` — fixed stem, no user-controlled component. Sweep-compatible by construction: `purge_expired_uploads` derives the id via `path.name.split("_", 1)[0]` + `_TEMP_ID_RE.fullmatch`, and `cleanup_temp`'s extended `{temp_id}_*.db` glob matches. Docx naming unchanged (long-name behavior pre-existing, out of scope).
