### CL-1 — Refresh an Already-mounted Options Tab on Return (MEDIUM)

**Trigger:** open options at least once; switch to fields; create a dictionary via quick add; return to options without another global refresh.

**Confirmed cause:** lazy tabs remain mounted; invalidating an API cache does not replace another mounted consumer's array, and returning to options currently performs no local re-read.

Evidence:
- `frontend/src/App.vue:224-237,937-949`: activation/retained host; `frontend/src/composables/useLazyTabs.js`: retained `activatedTabs` state.
- `frontend/src/components/CodelistsTab.vue:44-59,120-123`: load/reload and mount/project/selection/global-refresh watchers, with no reactivation load.
- `frontend/src/composables/useApi.js:119-153,216-243`: request-cache invalidation is not a consumer-state broadcast.
- `frontend/src/components/FieldsTab.vue:379-405` and `frontend/src/components/FormDesignerTab.vue:3746-3782`: add branches avoid a global broadcast; edit branches still use it.
- `frontend/tests/component/CodelistsTabBehavior.spec.js:148-155`: manually increasing `refreshKey` covers the existing watcher, not the producer path. `frontend/tests/fieldsTabCodelistQuickEdit.test.js:49-55` intentionally distinguishes add-transition behavior from edit-time global refresh.

**Required outcome:** a local guarded refresh when returning to options, with one initial load and retained current selection if that dictionary still exists. Reject departed project/auth/component lifetimes and superseded reads, including A→B→A. Preserve drafts, input, search and history elsewhere; do not add unconditional `refreshKey++`, reload other editors, advance their write baselines or auto-select the new dictionary. Current refresh failure retains previous visible data and reports failure, while departed operations produce no late feedback. This is application-tab refresh, not browser-multitab live collaboration.

### CL-2 — Distinguish Committed Creation from Failed Refresh in Both Hosts (MEDIUM)

**Trigger:** quick-add POST succeeds, then a required consistent/fallback read fails while the originating operation is still current.

Evidence:

- `frontend/src/components/FormDesignerTab.vue:528-532,3746-3782`: guarded fallback reads can throw. **Required outcomes:**
1. Keep genuine creation failure separate from refresh failure. A current failed POST retains original dialog/input for correction. No automatic POST retry is allowed.
2. For committed creation followed by actual refresh failure, finalize only the original dialog into a non-resubmittable terminal state and give exactly one unambiguous warning: `字典已创建，但列表刷新失败，请刷新后核对，勿重复新增。` Do not add a competing host load error or ordinary success/creation-failed toast. The risk is misleading manual resubmission, not an existing automatic duplicate POST.
3. Bind only a verified current candidate. If a read succeeds but the created id is absent, do not bind or pretend creation failed; report already-created/not-currently-visible feedback instead. Missing transition metadata alone is not a business failure; successful compatibility fallbacks remain supported.
4. Cancellation, selection/editor changes, project A→B→A, auth changes, unmount or dialog replacement must not rebind stale data, close/reset a newer dialog, clear its input or emit old completion feedback. Preserve original-project cache invalidation for committed writes and existing quiet original-modal-only finalization where appropriate. An older finalizer cannot affect a newer submission's busy state.
5. Preserve exact transition-candidate proof, paired snapshots, normal success wording/order and conservative later review across unproven gaps. The new error/notice policy is codelist-add-specific; unrelated ordinary-load, unit, copy and reload behavior is unchanged.
